# Full-system verification & load campaign — 2026-11-05

**Verdict:** no crash. The system degrades under a 2,000-concurrent burst but
survives, and the two availability defects found (event-loop body-parse DoS,
pool exhaustion as HTTP 500) are fixed and re-measured. All functional layers
passed: unit, live HTTP against real Postgres, role/authorization matrix,
ACID races, and a real-browser walk of all three portals.

Executed against an isolated `joblinked_bench` database (schema + reference
seed + 50k jobs / 20k seekers / 60k applications / 200k notifications / 200k
audit rows) and a second API on `127.0.0.1:4100`. The demo database was never
touched. Real Supabase sessions were minted for the `@joblinked-spike.test`
fixtures.

Environment caveat: one developer laptop (12 cores, 16 GB), Postgres 18 on the
same machine, one Node process, pool max 20. Numbers measure this box, not
production capacity. They are comparable across runs because every run used the
same dataset and hardware.

**Suite stability note.** One frontend test
(`src/features/super-admin/__tests__/Dashboard.test.jsx > shows an alert when
getStats rejects`) hit its 5 s default timeout on two full-suite runs under
heavy parallel load, then passed 5/5 standalone and 918/918 on the repeat full
run. It is environment-sensitive, not related to these changes. Worth raising
its timeout if CI runners are small.

The live suite is not mocked: every request goes over HTTP; every assertion
about persistence is read back from Postgres. It covers every route group
(auth, jobs, applications, profiles/uploads, admin, reports, notifications),
the authorization matrix (seeker / employer / other-employer / admin /
anonymous), UUID and enum guards, transaction triggers
(`employment_history`, accreditation sync), CSV injection escaping, path
traversal, CORS, helmet, oversized payloads, malformed JSON, and rate limiting.

The browser suite signs in with real passwords, clicks every sidebar item in
Seeker (8 pages), Employer (7), Super-admin (13), and fails on any console
error, page error, or failed request. It also asserts real data
(“Bench Published A2” appears in the seeker's applications).

Concurrency checks: 23 seekers apply to one job simultaneously (23 rows);
one seeker fires 10 duplicate applies (exactly one 201, nine 409, one row);
20 parallel job creates (20 rows); three competing status transitions
(three history rows, one `employment_history`); concurrent accreditation
submits. All passed.

## 2. Findings and dispositions

| # | Severity | Finding | Status |
|---|---|---|---|
| D1 | **High** | A suspended account could not be reinstated: `findUserTable` picked the stale `inactive` row in a higher-precedence table, answered 200, and left the real row suspended. Proven live (PATCH 200 → seeker `suspended`, employer `active`). | **Fixed** (ADR-039) |
| D2 | **High** | Unauthenticated event-loop DoS: `express.json` ran before all limiters. A 900 KB-body flood from one client pushed `/api/health` to p50 **8.6 s**. | **Fixed** (ADR-038) |
| D3 | Medium | Pool exhaustion surfaced as **500 INTERNAL** (1,991 `timeout exceeded when trying to connect` at 2,000 concurrency). | **Fixed** → 503 + `Retry-After` |
| D4 | Medium | Invite upstream failures were reported as `409 “email already registered”`; a Supabase rate limit looked like a permanent conflict. | **Fixed** → 429 / 502 / 400 mapping |
| D5 | Low/Med | `GET /api/admin/users` costs **203 ms** at 20k users (union + `to_jsonb` for every row before `DISTINCT ON`/LIMIT). Linear in user count. | Deferred; ceiling documented |
| D6 | Low | `db/migrations/004_remove_shortlisted.sql` is **not** re-runnable on a current schema despite its “safe to re-run” header: it casts `'Shortlisted'`, which the current enum no longer contains (22P02). Fresh installs must follow `db/README.md` (schema + seed). | Deferred (docs/migration hygiene) |
| D7 | Info | Public list runs an exact `count(*)` on every page: 8–14 ms at 45k published jobs. Grows linearly; a 1M-row board would spend ~200–300 ms/page. | Documented; optimize when data grows |
| D8 | Info | `apiLimiter` is 300 req/15 min **per user across all endpoints**; an active SPA session hit 429 after ~150 rapid calls shared with a second page's requests. Product decision, not a defect. | Needs product call |
| D9 | Info | 2,000 simultaneous **new** TCP connections produced 746 client-side `ECONNREFUSED` (listen backlog) in the first burst. The documented deployment has one proxy in front, which absorbs this. | Documented (ADR-037) |

Known/parked, re-confirmed but not re-fixed: `persistSession: false` signs the
user out on a hard refresh (owner-parked), and the address bar stays frozen at
the entry URL by design (ADR-035) — the browser harness therefore asserts DOM
state, not URL.

## 3. Functional coverage highlights (all green)

- Provisioning is idempotent; a forged body role can never create a
  super-admin (403); suspended sessions are gated on the next request.
- Jobs: drafts invisible publicly (404/LIST exclusion), owner/admin visibility,
  duplicate copies as draft, publish requires accreditation, `vacancies: ''`
  is 400 not 500, history rows written transactionally.
- Applications: deadline enforced in the INSERT…WHERE EXISTS (no TOCTOU),
  duplicate is 409, foreign resume 400, cross-tenant reads 403, status
  transitions write history + notify, `Accepted`/`Placed`/`Terminated` drive
  the employment trigger exactly once.
- Uploads: real 5 MB multipart, extension filter, missing file 400, PDF cap,
  one-active-resume index, owner/linked-employer file authorization, traversal
  refused.
- Reports: all 9 CSV types, correct headers/filename, formula-injection
  neutralised on a real stored `=cmd|calc!A1` name.
- Notifications: broadcast fan-out, owner-scoped read/read-all/delete,
  another user's id is 404.
- Role move: seeker → employer → seeker preserves applications, deactivates
  then reactivates rows, self-move refused.

## 4. Load results (jobs list, 45k published / 50k total, pageSize 20–100)

Anonymous ramp, 20 s per step, distinct client IP per worker:

| concurrency | throughput | p50 | p95 | p99 | 429s |
|---|---|---|---|---|---|
| 1 (sequential) | 34 rps | 21 ms | 42 ms | 247 ms | 0 |
| 50 | 477 rps | 101 ms | 153 ms | 193 ms | 0 |
| 200 | 469 rps | 411 ms | 557 ms | 668 ms | 0 |
| 400 | 493 rps | 783 ms | 990 ms | 1,497 ms | 0 |
| 800 | 542 rps | 1,506 ms | 1,964 ms | 2,077 ms | 1,262 |

Authenticated `GET /api/applications/mine`, 24 real sessions, 6,000 requests:
**1,179 rps**, p50 62 ms, p95 93 ms (the 300/15 min/user bucket is the real
ceiling for one user, by design).

Query plans: the page query is 0.1 ms (index scan); the exact count is 8–14 ms;
the admin-users union is 203 ms at 20k users. Throughput saturates around
**500 rps** for anonymous list traffic — the pool (20 connections × two
queries/request) and per-query count cost, not the event loop (lag p50 ~12 ms).

### Crash ladder, 2,000 concurrent, 30 s, pageSize 100

| | before fixes | after fixes |
|---|---|---|
| 200 | 6,603 | 5,323 |
| 500 | **1,998** | **0** |
| 503 | 0 | 92 |
| client ECONNREFUSED | 746 | 0 |
| server log | 1,991 pool-connect timeouts, 7 connection terminations | only `db_unavailable` 503s |
| health p50 during | 2.75 s | 2.24 s |
| process after | alive, RSS ~48 MB | alive, healthy, RSS settles ~50 MB |

Conclusion: the system does **not** crash. It saturates and sheds load. The
defect was the 500 status, now 503. At this concurrency, requests still queue
for 6–10 s; that is the capacity ceiling of one node, not a correctness bug.

## 5. Body-parse DoS, before and after

900 KB JSON body, 100 workers, 15 s, single client IP (so the throttle applies):

| | before | after |
|---|---|---|
| responses | 4,513 × 401 (every body parsed) | 300 × 401, then **7,759 × 429** |
| health p50 | **8,645 ms** | **164 ms** |
| health max | 10,261 ms | 973 ms |
| CPU | 15.8 s / 15 s | 14.1 s / 15 s |

The CPU figure barely moves because the kernel still receives the bytes; the
availability metric — can the process answer a health probe — improves 52×.
Bandwidth remains the theoretical vector for rejected uploads.

## 6. Reproduction

```bash

node server/.probe-bench-db.mjs        # schema + seed into joblinked_bench

# API on :4100 against the bench DB

# load
node server/scripts/loadtest.mjs --label jobs --url http://127.0.0.1:4100 \
  --route "anon:/api/jobs?page=1&pageSize=20" --duration 20 --concurrency 200 --xff --probe
```

`server/scripts/verify-live.mjs` and `verify-browser.mjs` are kept as
repeatable harnesses. The `.probe-*` scripts, raw result JSON, logs, token
files, and `.bench-dist` were scratch and are removed after this campaign.

## 7. Follow-ups worth scheduling, not blocking

1. **Admin users at scale (D5).** Move `to_jsonb(x)` after `DISTINCT ON`/LIMIT
   and join back for the page's 25 rows; expected ~10× at 100k users.
2. **Exact totals (D7).** Cache the count per filter set for a few seconds, or
   switch to an estimated count, if the board grows past ~200k published jobs.
3. **Per-user throttle policy (D8).** Decide whether 300/15 min is right for
   dashboards that load several panels at once; a higher authenticated budget
   with a burst allowance is the usual shape.
4. **Health under saturation.** A dedicated health connection (max 1, 1 s
   connect timeout) if a health-checked proxy is added.
5. **Migration hygiene (D6).** Make 004 detect the enum label before casting,
   or correct its “safe to re-run” header.

## 8. Not verified

- `POST /api/ai/help`: no `OPENROUTER_API_KEY` on this machine and it would
  call a paid external LLM. Its contract is covered by the unit suite only.
- Actual delivery of invite emails (Supabase email sending is rate-limited on
  the dev project; the API mapping is verified, the inbox is not).
- Multi-instance deployment, Redis-backed limiting, TLS termination, and
  proxy behaviour (single-node ADR-037 scope).
- Cross-browser rendering (headless Chrome only).
- Long-duration soak (> 30 s bursts); memory returned to baseline after each
  run, but a multi-hour soak was not run.
